### V088 — August 27–28, 2026

**A genuinely different kind of session than the ones before it — almost entirely refinement and real-bug-hunting on already-proven logic, not new capability.** No single dramatic validation day this time; instead, several real, separately-discovered gaps, each traced to its actual root cause before being fixed, plus a full new view (Account) built and shipped across several sessions culminating here.

**A real, live-observed max-loss miss led to a genuine architectural fix.** The user watched a position (WDC) cross its configured -0.3% threshold and keep falling — -0.27% → -0.29% → -0.31% → -0.37% → -0.47% → -0.53% — before finally selling, well past where it should have. Investigated methodically rather than guessed at: confirmed the console showed no errors and updated normally throughout (ruling out a silent series-fetch failure being *visibly* logged), confirmed the bot correctly caught a *different* position at the same threshold later the same day (ruling out anything systemically wrong with the comparison logic itself), which together pointed at something intermittent, symbol/cycle-specific. Traced to a real structural gap: the per-position max-loss check only ever needs `pos.pct` (Alpaca's own position data, already fetched once per cycle for every symbol) — but it lived *inside* the same `try`/`continue` block as the bar-series fetch, which it never actually needed. A symbol whose series fetch failed or came back short on a given cycle had its max-loss check silently skipped too, despite the check's own comment claiming it was "independent of the buy window and the master switch" — true, but silently *not* independent of the series fetch succeeding. Fixed by moving the check to run unconditionally, at the same level as the day-cap check, before any bar data is fetched at all — verified numerically against the exact bug scenario (a losing position with a failing series fetch) and three other cases, confirming no regression to the surrounding logic.

**A related but separate confusion, worth recording as its own distinct finding, not conflated with the bug above.** The user was confident the Positions table's visual red-hue warning had used the bot's own max-loss threshold — it hadn't. `lossAlertPct` (Settings, default -0.5%) and `maxLossPct`/`maxLossPctMorning` (the bot's own actual sell trigger) had always been two completely separate values, confirmed by an exhaustive search of every reference to each — zero code path connected them. A comment from early in this feature's own history had already flagged the exact overlap risk months earlier ("may end up overlapping with lossAlertPct in meaning... reconciling them is a later decision") — that reconciliation never happened until now. Resolved simply: `lossAlertPct` removed entirely as its own stored/editable value; the Settings field kept visible but made read-only, always showing `getEffectiveMaxLossPct()` live; all three display call sites (the top Positions stat card, each table row, the TOTAL row) now read directly from that same single function. One source of truth, nothing left to drift apart again.

**A real design conversation that went sideways once, and was explicitly, deliberately reset rather than patched through.** The user wanted a way to recover from a day-cap lockout without waiting for the next day, on the reasoning that being permanently locked out of the bot's own safety-netted trading — even when confident the rest of the day looks good — forces a fallback to fully manual trading with *no* safety net at all, the worst available option on exactly the day the user is most engaged and most likely to want to act. First design pass overcomplicated it (aggregate-vs-per-symbol distinctions that didn't actually apply here); the user's own "let's align on the premise before proposing a solution" and later "simpler please" reset it cleanly. The actual build turned out to need zero new comparison logic at all: `dayCapLockoutActive` was already a single, shared flag (confirmed by the user's own observation that both cap fields highlight together when either trips), and the existing evaluator already only re-checks today's P&L against the caps when the flag is `false` — so a manual "Off" toggle just sets the flag false, and the very next cycle naturally re-locks it if the caps weren't actually raised enough, with zero new code needed for that self-correction. Built as a toggle matching `manualNoBuyToday`'s own visual pattern, but deliberately asymmetric: "On" is disabled entirely (grayed out, unclickable) since only the bot itself should ever set that state — "Off" is the only real, user-initiated action. A real bug surfaced immediately after building it: the toggle's own populate logic checked only the raw flag, missing the same `isLive`/reason-filtering the existing amber highlight already correctly applied — so the toggle could show "On" in Sample mode or over a weekend while the highlight correctly showed nothing. Fixed by hoisting the shared `dayCapReallyActive` computation earlier in the same function so both the toggle and the highlight read from one single, unified value — they can no longer disagree with each other by construction.

**Max Loss/gain-protect cap (`maxLossCapDollars`) changed from an always-positive magnitude to a direct signed threshold.** Motivated by a real scenario: re-enabling the bot mid-day via the new clear toggle after Max Gain has already tripped, wanting to protect the gain already banked rather than only ever limiting fresh downside from zero. `todayPL <= -maxLossCapDollars` became `todayPL <= maxLossCapDollars` — a negative value behaves exactly like the old convention (e.g. `-20` locks out at -$20, same as the old positive `20`); a positive value now protects an existing gain instead (`+15` locks out if today's total drops below +$15). Bounds widened to ±$1000; label updated to reflect the dual purpose. Deliberately no auto-migration of the user's own existing saved value — "I will fix what is stored" — since silently reinterpreting an old saved number under a flipped sign convention was judged riskier than a one-time manual re-entry.

**Previous-close reference, shown top-right on Compare cards, not held.** Captured once per bolt-enabled symbol at the EOD trigger (15:55) — gated on both the master switch and the individual symbol's own bolt state, matching every other gate this evaluator already respects. Deliberately scoped with no fallback: only covers bolt-enabled symbols, only reflects whatever the workhorse device's own browser tab happened to capture — accepted as fine, since the workhorse device is always running and this was never meant to sync across devices. Stored as a raw price, not a pre-computed percent, so the displayed comparison stays live and accurate as the current price moves throughout the day rather than freezing at capture time. Displayed as a second, aqua-colored (`#4FD1C5`) percentage appended after the existing session delta — `innerHTML` with a nested span, since the two segments need different colors and `textContent` can't carry that. Worth being honest about one approximation: 15:55 is a few minutes before the session's true 4:00 PM close, so the captured value is the latest available bar, not a precise closing price — acceptable given this is explicitly reference-only, never read by any trading decision. Sample mode shows a plain aqua "-" instead of silently omitting the segment, so the layout itself previews correctly even without live data behind it.

**Today card's own % now reads against a configured daily $ goal when one's set, reusing `accountDailyTargetDollars`** (the same value already driving the Account chart's own target line) rather than a second, separate setting — deliberately left in its current Settings location rather than relocated pre-emptively, on the user's own reasoning that if it turns out to need moving, that'll be obvious once it's actually serving two purposes, not worth guessing at now. Deliberately a different scope from the bot's own Max Gain cap, since raising that cap mid-day via the clear toggle shouldn't silently move what the card considers "the goal." Falls back to the original equity-based % whenever no goal is configured, unchanged from before. A small additional guard added during the build: the goal input has no `min` constraint, so an accidental zero or negative value is explicitly checked for and falls back to the equity-based percentage rather than producing a divide-by-zero or a misleadingly-signed number.

**Clock click-to-reload, matching the user's own prior app.** `window.location.reload(true)` wired to the wall clock, with `cursor:pointer` and an explanatory tooltip — the specific fix for iOS home-screen web apps otherwise silently continuing to run a stale, cached version after a new one's been deployed, requiring a full app kill to pick up new code otherwise. The whole stat-card row (including the clock) gets torn down and rebuilt every account-refresh cycle, so the click listener has to be reattached every single time, same pattern already used for the liquidate button right next to it.

**A real self-introduced bug caught and fixed while adding a Refresh button to the Account view.** Making the view's header rebuild unconditional (so the button stays present even on error/empty-data paths, matching the activity-summary's own pattern) meant the panel's `innerHTML` got wiped on every single call, including ordinary successful re-renders — but the module-level ApexCharts instance variable wasn't being reset to match, so a second call (like clicking Refresh) would try to update an orphaned instance no longer attached to any visible DOM element, silently failing to render at all. Same failure shape already caught and fixed on the error/empty paths once before, reintroduced here by a different change — closed with a single unconditional `destroy()` at the very top of the function, which also let the now-redundant destroy calls further down get removed. Verified numerically across three consecutive simulated calls (including two simulated Refresh clicks) — a genuinely fresh chart instance created every time, never an orphaned update attempt. Deliberately no fix to the view's own signature-based re-render caching (a real, separate gap where switching to Account without any of the unrelated caching inputs changing could silently skip a fresh fetch) — the manual Refresh button was judged sufficient on its own, and no 4am auto-refresh was built, on the same reasoning.

**Help fully updated to match all of the above**, closing several real, pre-existing gaps found along the way, not just documenting what changed this session: the Account view had never been in Help at all despite existing for several sessions already: the Today/Positions stat cards' own percentage behavior had never been documented in any form, old or new.

### V078 — August 22, 2026

**Ten refinements this session, all traceable back to the state-based redesign actually holding up under a real, difficult trading day.** Trust earned from that validation showed up directly: the invest ceiling raised again (150 → 5000), and the day proceeding largely without needing to second-guess the core buy/sell decision at all. Caught and fixed before it ever shipped. Separately, the buying-power check's first draft let a buy proceed if the value came back unreadable rather than genuinely insufficient — a fail-*open* default that broke from the fail-closed pattern every other gate in the evaluator follows. **The day-cap visual indicator went through the most real iteration of the session, driven entirely by a live screenshot showing something that didn't match the mental model.** First build: hidden unless `dayCapLockoutActive`, on the general Settings-page pattern of a separate status row. And the "Today" button label itself turns the same amber used for the day-cap indicator whenever a historical date is active, with a tooltip spelling out the real consequence — sell/max-loss monitoring paused, not just buying.

### V077 — August 21, 2026

**The reconciliation redesign — the fix for V076's known limitation — is built and confirmed live on its first real trading day, under genuinely difficult market conditions.** The old rule asked "did a transition just happen"; the new rule asks "does current state match held state, fix it if not." That single reframing closes the exact gap that caused three confirmed missed trades the day before: a bar's settling correction landing such that it had already shifted from "current" to "previous" by the time the fresh-transition rule looked at it again. Reconciliation doesn't care when a move started — only whether it's still true right now — so an already-established trend that the old rule would have permanently missed gets caught on the very next check instead.

**The two functions that were split apart in V076 came back together, for a precise, non-obvious reason.** Day-cap/max-loss were sped up to run every minute specifically because crossover-detection needed to stay slow, to avoid reacting to noise — that was the whole justification for two separate cadences. Reconciliation removes that justification entirely: it needs to re-check every minute too, since there's no "freshness" concept left to protect. Consolidating back to one function, one fetch, was verified numerically before being trusted, not just assumed convenient: the -2/-3 bars themselves only genuinely change once every five minutes regardless of how often they're checked, so running the check every minute is strictly a detection-speed improvement, never a change in what's actually being evaluated.

**The specific risk this design was known to create — reconciliation immediately buying back into a position a day-cap lockout had just forced closed — was solved before it was ever built, not discovered after.** Two rounds of pseudo-code from the user surfaced this directly: the first draft only guarded a *held* position from day-cap, leaving a freshly-sold one able to re-buy the very next cycle; the second draft fixed it by gating the entire per-symbol block on lockout state, before any bar data is even read. Verified numerically before shipping: a bar reading green the cycle immediately after a day-cap sell correctly does not trigger a buy-back.

**Two corrections happened in conversation that are worth recording honestly, not glossing over.** A pseudo-code review of a stub value (`max_gain_exceeded`) surfaced what looked like a new per-position max-gain concept — confirmed by the user to be a naming slip, not a real idea, and removed cleanly rather than built around. And the deadband's boundary semantics briefly became a real point of confusion between the two of us — a question about the *buy-window* boundary was misread as being about the *deadband* boundary, answered incorrectly, then caught and reverted before it shipped.

**Live validation today was more meaningful than a clean winning day would have been.** The user described today as "one of those days where it is hard to make money trading, even if it was me" — and that's precisely the condition that tests loss control rather than luck. SMCI was bought by reconciliation directly, confirmed against a real chart showing exactly the established-trend pattern the redesign targets. During a known-choppy 9:45-10:00 window the user doesn't normally trade, every held position was sold with minimal, contained loss — the specific failure mode this redesign exists to prevent (a real exit signal silently missed while a loss keeps accumulating) simply didn't happen. Three independent surfaces — console, chart, and Positions view — all agreed with each other and with the user's own market read, across the whole session.

**Also raised today for the first time, not yet acted on:** whether a single positive/negative deadband is the right model at all, or whether momentum up and down are different enough in nature to warrant separate numbers — explicitly deferred, since reasoning about it before real data existed would have been guessing. The hard trading day itself is what's sharpening that intuition; being logged now specifically so it isn't lost, not because it's ready to be built.

**Explicitly not validated today, and worth tracking honestly rather than assuming covered by the rest:** Max Day Gain and Max Day Loss did not fire — deliberately, since today's caps were sized for a scenario (positions manually grown toward $1000) that today's test intentionally wasn't running, to avoid confusing two different things being validated at once. End-of-day sell (15:55) also remains unexercised live on any date so far. Both are still resting entirely on last night's numerical verification, not yet on a real trading day.

**One other change today:** the hardcoded invest-dollar ceiling was raised from $100 to $150, asked for directly and changed at the single source of truth exactly as its own original comment said it would need to be — sub-$100 orders weren't reliably filling in practice. Verified numerically that the new ceiling holds at every enforcement layer, and that a smaller configured value is never forced upward to meet it.

### V076 — August 20, 2026

Real-world use surfaced something the design phase couldn't have: **transition-only crossover detection has a genuine, recurring blind spot, not a rare edge case.** Confirmed directly by the user — three separate times in one trading day, across different symbols, a real buy or sell point never registered as a *fresh* crossover by the time its settling bar was actually evaluated, because by then it had already become the "previous" bar in the next comparison rather than the "current" one. The cost is asymmetric and real: a missed buy is lost opportunity; a missed sell can mean a real, accumulating loss with nothing watching it. This is now an open, actively-being-designed-around limitation, not yet resolved — see below.

**Two smaller, high-value additions this round, both built the same way as everything else — verified with real numbers before being trusted.** First: max-loss and day-cap checks were split into their own function (`evaluateFastRiskChecks()`), running every minute instead of every five, since a real position moving from +0.01% to -4.8% inside a single 5-minute gap had gone completely uncaught. Safe to speed up specifically because it reads only account/position data, never the bar series that crossover's own noise-avoidance logic depends on. Second: a deliberate, deep dive into how the underlying bar data actually behaves — confirmed directly from the code's own comment that the most recent bar in any fetch is *always* still-forming, never settled, not occasionally but structurally. That reframed the original crossover logic's index math as comparing an in-progress bar against a barely-settled one on every single cycle, not as an edge case. Fixed by shifting the evaluation window one minute later and comparing bars at index -2/-3 instead of -1/-2, deliberately leaving the blue five-minute cue's own timing untouched, since its meaning was never part of this fix.

**Both changes were proven with concrete simulations of the user's own exact scenarios before being trusted, not just reasoned about.** The bar-settling fix in particular was validated against a literal reconstruction of a real missed-buy sequence — old logic misses it at both checks, new logic catches it — and a real structural bug (an `if`/`else-if` collision that would have silently defeated the fix in the exact configuration being used) was caught mid-build by the user's own question about the timing, not discovered afterward.

**A third feature, `deadbandOverrideSymbols`, closed a gap the deadband visualization itself had surfaced earlier: a single flat threshold reads very differently across symbols of different natural volatility.** Deliberately scoped small — one override group, not a general per-symbol system — and deliberately chart-display-only: the actual crossover decision logic never reads it, confirmed directly by tracing `classifyDelta()`'s own callers. The real clarifying moment wasn't the mechanism, it was the meaning: this list isn't "symbols needing a different number," it's inherently "symbols I do not plan to auto-trade" — which settled several smaller questions (the bolt toggle stays completely untouched, no hiding, no gating) in one move rather than needing separate answers for each.

**A live, real-money session this morning confirmed the existing design works exactly as built — and, in the same session, surfaced its most significant known gap.** Both things are true at once: the fail-closed gates, the $100 cap, the day-cap lockout, and the crossover logic all performed as designed on real trades, and separately, the transition-only limitation above showed up three times in the same session. Next design conversation, not yet started as code: reframing crossover from "did a transition just happen" to "does current state match held state, reconcile if not" — which would close the miss but requires deliberately teaching it to respect a day-cap or max-loss exit, or it would immediately buy back into a position the lockout was specifically meant to stop touching.

### V074 — August 19, 2026

Since V061, the project's center of gravity shifted entirely: from polishing an already-working watchlist app to designing, building, and — as of today — **validating with real money** a full automated-trading feature. The throughline across all of it: **design before code, verify with numbers not assertions, and trust a real screenshot over an abstract argument whenever the two disagree.**

**The design phase came first, deliberately, and paid off directly.** Rather than a spec, the feature emerged through incremental scaffolding (`getHMM()` as inert infrastructure, then the bolt toggle as a pure setting with no execution behind it yet, then finally "let's go through the logic together") — each piece giving the next something concrete to react to. This wasn't padding: it's what let the user catch, unprompted, that the buy window was silently also gating sells (a real bug that would have left a losing position unwatched exactly when it mattered), and that "sell on a red bar" needed to mean a *crossover* — a fresh transition, preceded by a *non-red* bar — not a static color, which is what makes the rule fire once per direction change instead of repeatedly through a whole losing stretch. A written design doc (`uptick-automated-trading-logic.md`) captured every resolved decision before any of it became code, specifically so it could be reviewed and revised before the stakes went up.

**Every gate is fail-closed, verified exhaustively, not just written.** `evaluateAutomatedTrading()` (§12) is wrapped in nested try/catches; any error — a failed positions fetch, a malformed series — aborts that pass with no action, never a fallback assumption. The $100 invest cap is enforced at four independent points (HTML `max`, Settings save-time clamp, restore-from-storage clamp, and the buy execution's own independent clamp) referencing one shared constant, proven numerically that even a config value that somehow bypassed the earlier layers still can't slip through the last one.

**Two real bugs were caught before they ever shipped, both by careful re-reading rather than by luck:**
- `executeSell()` calls a blocking `confirm()` — reusing it from automated logic would have frozen an unattended page indefinitely, since `confirm()` blocks the JS event loop and nothing is there to click it. Caught by re-reading the function before wiring it in; automated logic calls `TradingAPI.buy()/sell()` directly instead, which were already prompt-free.
- The end-of-day sell trigger originally used `else if` against the normal eval-second trigger. Since both defaulted to the same second (59), the `else if` meant the EOD-specific "sell unconditionally" behavior would have silently never fired in the default configuration — the normal branch would always win the tie, and the position would only sell if a crossover or max-loss trigger *also* happened to be true at that exact moment. Fixed to two independent `if`s before it ever reached the user.

**The three-color deadband chart visualization (§5) turned into a genuine research tool, not just a bug-fix.** It was built to answer "why didn't this fire" after a real discrepancy between the chart's old two-color coding and what the logic actually evaluated — but once built, comparing it across several real symbols side-by-side surfaced that a single flat deadband means something very different depending on a symbol's natural volatility (QQQ reading as almost entirely neutral under the same threshold that gave SOXL a healthy, balanced mix). That's now open, explicitly-deferred research, not a settled number — the visualization did its job by making the question askable in the first place.

**Day caps (§12) went through a real design reversal, not a straight build.** The first version ("stops buying, does not force-sell") was reasoned from the bolt-toggle's existing "stop ≠ sell" principle — but that analogy didn't actually fit. The bolt toggle is a narrow, per-symbol decision; the day cap is modeled on genuinely quitting for the day, which means being fully out, not paused-with-exposure. Revised to liquidate and lock out, with the lockout deliberately sticky through the session (verified numerically against the exact scenario that motivates it: a sell settling below the triggering value, thanks to spread, must not read as "back under the cap, resume").

**Visual fixes repeatedly demonstrated the same lesson from both directions.** The bolt toggle's icon color went through several real iterations — WCAG contrast math favored a dark icon, but real screenshots showed it disappearing into the fill; white was tried next based on that same visual evidence, and held up even once the math for the *other* fill color was checked too. Separately, an "armed" state built with `opacity:.45` was diagnosed as a genuine CSS problem for two full rounds before the real explanation surfaced: it was working exactly as designed, correctly dimmed because the screenshot was taken outside the configured trading window — not a rendering bug at all. Both threads ended the same way: trust what's actually on screen, and verify the actual state before assuming the code is wrong.

**Today, live: the design was confirmed against real trades, not just against tests.** The bot bought (capped at $100) and later sold a position on its own, matching the crossover logic exactly as designed weeks of conversation earlier. A separate, related scenario also got exercised for real: a bot-bought position that the user then manually added to (bringing it from $100 to $1000) was still correctly monitored by the bot's sell logic — confirmed directly from the code that the bot reads one shared, blended position from the broker, with no concept of "whose share is whose," and that a sell would close the entire position, manual addition included, not just its own original portion. End-of-day sell (15:55) was not exercised today — too early in the session for that specific trigger to have come up — and remains unverified live, though numerically confirmed at build time.

Two safety gaps were found and closed *after* the core feature already existed, each surfaced by the user thinking through a scenario the original design hadn't considered: importing settings onto a second device would have silently carried over an armed master switch and enabled symbols from the exporting device, since export/import predates automated trading and was never built with it in mind — fixed by forcing those specific fields off on import while preserving the numeric configuration. And the blue five-minute cue and the bot's own execution both used to span a broader 4am–8pm `isLive` window rather than actual regular trading hours — narrowed with a new, additional, shared gate rather than touching `isLive` itself, since that broader definition is still genuinely needed elsewhere (chart refresh, historical-date detection).

## 1. Config & State

**`CONFIG`** — the one object holding every setting: `dataMode` ("sample" | "api"), symbol/account API URLs and credentials, `smaPeriod`, `lossAlertPct` (default -0.5, drives three separate hue treatments from one value), two independent refresh rates (`chartRefreshSeconds`, `accountRefreshSeconds`), and `autoTrading` (full detail in §12).

**Top-level state variables**:
- `TICKERS` / `selectedTickerIds` — the watchlist roster and which of them are checked
- `tickerPresets` — named snapshots of `selectedTickerIds` ("symbol groups")
- `currentTf` / `currentView` / `displayWindow` — Timeframe, active view (`trend` | `compare` | `table` | `research` | `positions`), and the "Today" hour-window slice
- `selectedDate` — a picked historical date, or `null` for live ("pretend this day is today")
- `researchSymbol` — the Research view's currently-applied search
- `heldPositions` — `Map<symbol, {dollar, pct, costBasis, currentPrice}>` from the live positions array (fixed, non-moving stub for 3 tickers in Sample mode)
- `autoTradeEnabledIds` — which tickers are bolt-enabled for automated trading, same `Set` pattern as `selectedTickerIds` (§12)
- `controlsExpanded` / `statsRowExpanded` — the two collapsible accordions, now persisted (a real preference reversal after real iPad use — always-expanded-on-load turned out to be more friction than the original "don't confuse a later session" concern was worth)
- `seriesCache` / `viewSignatures` / `viewMeta` — caching layers, covered in §7
- `selectedDateSetAt` — timestamp of when `selectedDate` was last set to a real date, distinct from `lastActivityTime` (which updates on any click at all) — drives a 4am trading-day-boundary reset alongside the existing 60-minute inactivity one (§8)

**Persistence** (`loadSettings()` / `saveSettings()`): everything above except `selectedDate` and `researchSymbol` gets written to one `localStorage` key (`uptick-settings-v1`) as a single JSON blob. Import deliberately overrides parts of this blob before it's ever written — see §12's safety notes.

## 2. Date & Session Logic

**`effectiveToday()`** — the single choke point every date function routes through: returns `selectedDate` if picked, otherwise the real current moment.

**`mostRecentTradingDay()` / `previousTradingDay()` / `tradingDayNDaysAgo(days)`** — weekday-aware date walking for the daily-bar windows (10D/30D/90D/180D), anchored through `effectiveToday()`.

**`getSessionWindow()`** — simulates a real trading session (4:00 AM–8:00 PM), holding at the last completed session outside that window. Returns `{sessionStart, sessionEnd, sessionNow, isLive}`. When `selectedDate` is set, always returns `isLive: false` — one flag disabling Buy/Sell, pausing chart auto-refresh, and hiding the held-position dot, all from a single source.

**`getSeriesWindow(tf)`** — computes fetch boundaries: `wideStart` (extra lookback so SMA has real history) and `displayStart` (the actual shown boundary).

**`trimToDisplayWindow()`** — trims `times`/`close`/`sma` together once SMA is computed on the wider set.

**`applyDisplayWindow(data, windowKey, tf)`** — "Full Day" / "9:00–4:30" / "Last 6H." Anchors to the data's own last timestamp, not `getSessionWindow()` — self-contained, and future-proofed for eventual historical-day browsing.

## 3. Sample Data Generator

**`generateSample(symbol, tf)`** — synthetic data, seeded (`mulberry32` + `hashStr`) so the same symbol+timeframe always generates the same shape, with a small live-tick jitter on the last bar while `isLive`.

**`sma(values, period)`** — before the window is full, each point defaults to its own close, so `close − SMA` is exactly 0 during warm-up.

## 4. DataSource, TradingAPI & Account

**`DataSource.loadSeries(symbol, tf)`** — branches on `CONFIG.dataMode`, then on `CONFIG.api.activeSymbolSource` in Live mode:
- **Source A** (your own proxy) — path-based URL, no auth. Optionally appends `?token=` from `CONFIG.api.symbolToken` if set — security through obscurity, not real access control; the backend already reads the parameter but ignores it until populated with something checked server-side against an allowlist. Never appended to Source B.
- **Source B** (Alpaca directly) — a genuinely different request shape: query-string params (`symbols`, `timeframe`, `start`, `end`, `feed=iex`, `limit=5000`, `sort=asc`), account credentials reused as auth headers (not a separate symbol-data credential), base URL defaults to Alpaca's real endpoint but is overridable via the same Settings field for a future version bump.

Both paths coerce `close` to `Number()` and normalize the last intraday bar's timestamp to a clean 5-minute boundary. Cached in `seriesCache`, keyed on `symbol|tf|selectedDate`.

**`DataSource.loadAccountInfo()`** — Live mode fetches `/v2/account` + `/v2/positions` in parallel, populates `heldPositions`, returns `combineAccountAndPositions()`'s dollar-weighted aggregate — now including `equity` and `buyingPower`, both read directly from the same `/v2/account` response already being fetched here, no additional network call for either. Sample mode's equivalent returns `null` for both — no plausible value to fabricate the way price drift stands in for a real quote elsewhere, so the display layer shows "-" for either.

**`TradingAPI`** — `buy()`, `sell()`, `liquidateAll()`.

**`executeSell(symbol, btn)`** — shared by Compare's sell buttons (id-based) and the Positions table's sell buttons (symbol-based directly, since a held position isn't guaranteed to be in the configured watchlist). Awaits `renderAccountRow()` internally so `heldPositions` is guaranteed fresh by the time it returns.

**`marketSessionAnnotations()`** — dashed pink lines at Open (9:30)/Close (4:00).

## 6. Views

Five views, one shared title/stat-row area:

- **`renderTrend()`** — Combined. Averages each selected ticker's own % change and SMA into one composite line.
- **`renderCompare()`** — one tile per ticker: chart, symbol color, held-position dot + $/% gain (live-only), Buy/Sell, and the automated-trading bolt toggle (§12) — three solid, fully-opaque states (off/armed/active), no `opacity` transparency anywhere.
- **`renderTable()`** — start/end/delta for the current window.
- **`renderResearch()`** — one-off symbol lookup, separate from the watchlist.
- **`renderPositions()`** — actual open positions, independent of ticker selection/timeframe/window. Symbol, $ Change, % Change, Cost Basis, Sell — reordered and Current Price dropped from display per explicit request ("not useful, just focused on making money"), though the field stays in the underlying data. A blue bolt icon prefixes the Symbol cell when that position's ticker is currently bolt-enabled — a read-only indicator, no click handler, reusing `autoTradeEnabledIds` directly rather than any new state; correctly resolves to false for a held symbol outside the watchlist entirely. Loss-alert hue applies per-row and on TOTAL independently — a single bad position doesn't get masked by an otherwise-fine total, and vice versa. Bypasses the view-signature cache entirely (cheap to rebuild; depends on data that updates on its own refresh cadence, not anything the cache key tracks).

**`render()`** dispatches on `currentView` via `currentSignature()`, and mutes whichever controls don't apply: ticker chips + symbol groups on Research and Positions; timeframe bar + window bar on Positions only.

## 8. Symbol Groups, Watchlist Management & the Historical Date Picker

**`renderTickerPresetRow()`** — a preset is a named snapshot of `selectedTickerIds`, never a separate ticker list. Saving under an existing name updates it *in place* now (fixed today — was previously removing-then-appending, silently moving the group to the end of the row). Muted whenever Research or Positions is active.

**`renderTickerManageList()`** — add/remove/reorder the watchlist roster via a staged `draftTickers` array. Reordering is up/down arrows, not drag-and-drop.

**The historical date picker** (`selectedDate`) — calendar icon on the Today button, its own click zone. Picking a date applies to whatever timeframe is already active. Picking today's actual date collapses back to `null` rather than staying a technically-non-null "historical" state. Two independent resets converge on the same `resetSelectedDateToLive()` helper: the existing 60-minute click-based inactivity timer, and a newer 4am trading-day-boundary check — added after tracing a real, previously-unnoticed risk: `getSessionWindow()` returns `isLive: false` whenever a historical date is picked, and the evaluator's own timer trigger requires `isLive` to fire at all, so a historical date left selected doesn't just pause new buys, it silently stops sell/max-loss monitoring on anything already held. ## 9. Auto-Refresh

Two independent wall-clock-aligned timers (`second % rate === 0`, checked on a plain 1-second tick):

- **Chart refresh** — gated on `getSessionWindow().isLive`.
- **Account refresh** — *not* gated on `isLive`. Runs 24/7.
- **Automated trading evaluation** (§12) — a third, separate condition on the same 1-second tick, firing once a minute (no five-minute-mark requirement, since the state-based decision removed the reason that requirement existed), requiring `isLive` and gating on regular hours internally. A fourth, independent `if` (deliberately not `else if` — see §12) handles the 15:55 end-of-day trigger. A brief third trigger existed for one day (August 20) when day-cap/max-loss ran on their own separate, faster cadence via `evaluateFastRiskChecks()` — removed when the state-based redesign consolidated everything back into one function on one cadence (see §12, V076 history).

A separate 200ms interval (`updateRefreshBar`) animates the countdown bar, and also drives the five-minute checkpoint highlight on the Today card (`.five-min-active` — steady, not pulsing, deliberately, so the cue meant to reduce reactive decisions doesn't become a source of it itself). This cue now requires regular trading hours specifically (930-1559), not just `isLive`'s broader 4am-8pm span — narrowed on request, since it was being read as "the bot could be active right now," which stopped being accurate once the bot's own execution got a separate, additional hours gate. `isLive` itself is untouched; only the cue's own display condition and the evaluator's execution gate were narrowed, each independently, sharing one set of constants rather than two that could drift apart.

A related concern was raised and investigated, then closed without a code change: whether switching the UI's own timeframe view (`currentTf`) while the bot trades could feed the evaluator wrong data. Traced directly rather than assumed either way — the evaluator's own series fetch is hardcoded to the literal string `"today"`, never reads `currentTf` at all, so the two are already fully decoupled.

## 10. Formatting & Sign Handling

**`round2(v)`** (`Math.round(v * 100) / 100`) — every display-facing rounded number in the app routes through this first, rather than trusting `toFixed()`'s own rounding, which can disagree with "round half up" on exact half-cent boundaries.

**`signOf(v)` / `signColor(v)` / `signPrefix(v)` / `signClass(v)` / `upDownNeutral(v)`** — determine up/down/neutral coloring based on the *rounded* value, not the raw one. Added today after finding a raw value like `-0.001` would display as `"0.00"` while still coloring red, since the color decision used the un-rounded number. All 16 sites in the app that made this kind of sign-based decision — stat cards, Compare tile color/gain, Table view, Research stats, Positions rows/TOTAL — now route through these instead of each doing its own `>= 0` check. `upDownNeutral()` specifically preserves `null` ("no data yet," e.g. CHANGE before a second update) as genuinely distinct from `"neutral"` (rounds to exactly zero) — collapsing those two would have been a regression, not a fix.

## 12. Automated Trading

**`CONFIG.autoTrading`** — `masterEnabled` (default false, local to this device only — export/import forces it off on import, see below), `startHmm`/`endHmm` (buy-only window, default 930/1559, three-layer clamped: HTML `min`/`max`, save-time, restore-time), `investDollars` (default 100, hardcoded ceiling of 5000 — see below), `evalSecond` (default 59), `maxLossPct` (per-position, default -1, the afternoon/all-day default), `maxLossPctMorning` (`NaN` by default, meaning "same as `maxLossPct`" — an explicit value applies only before the fixed 11:30 cutoff), `deadbandPct` (default 0.25, percentage points either side of zero counted as neutral), `deadbandNegPct` (`NaN` by default, meaning "same as `deadbandPct`" — an explicit value gives the negative side its own threshold), `deadbandOverrideSymbols`/`deadbandOverridePct` (chart-display-only override for a small, deliberately single group of "watch, never auto-trade" symbols — see below), `maxGainCapDollars`/`maxLossCapDollars` (account-level day caps, default 100 each, range-clamped 0-10000/0-1000 respectively, input step 5 — loosened from step 10 on 2026-08-24, since the original increment only made sense assuming exactly $100/symbol, an assumption the $5000 ceiling raise had already outgrown), `dayCapLockoutActive`/`dayCapLockoutSessionKey` (sticky lockout state, not user-editable), `dayCapLockoutReason` (`"gain"`/`"loss"`/`"eod"`/`null` — tracks *why* the lockout flag is set, purely to decide whether the UI shows an indicator, never to display the reason itself), `manualNoBuyToday`/`manualNoBuyTodaySessionKey` (a separate, freely-reversible lockout the user can toggle on and off directly — see below), `trailingPct` (disabled field, stays `NaN`). `autoTradeEnabledIds` is a separate top-level `Set`, same pattern as `selectedTickerIds`, persisted independently.

**Hardcoded constants** (declared early, alongside `controlsExpanded`, specifically to avoid the temporal-dead-zone `applySavedSettings()` IIFE would otherwise hit reading a `const` declared later in the file): `AUTO_TRADE_MAX_INVEST_DOLLARS` (5000 — raised 100→150 on 2026-08-21 when sub-$100 orders weren't reliably filling, then 150→5000 on 2026-08-22 once the state-based redesign held up on a genuinely difficult live trading day; referenced by every enforcement point, not settings-editable — raising it further means changing this constant directly, never a UI toggle), `AUTO_TRADE_EOD_HMM`/`AUTO_TRADE_EOD_SECOND` (1555/59), `AUTO_TRADE_REGULAR_HOURS_START`/`_END` (930/1559, shared by the evaluator's own execution gate and the blue five-minute cue's display condition — one source of truth so the two can't drift apart), `AUTO_TRADE_MORNING_CUTOFF_HMM` (1130, fixed and not settings-editable, per explicit instruction — only two windows, not adjustable), `AUTOTRADE_LOG_GREEN`/`_RED`/`_GREY` (console `%c` badge styles for the four decision-outcome log lines).

**One function again, not two — the state-based redesign removed the reason they were ever split.** `evaluateFastRiskChecks()` and `evaluateAutomatedTrading()` briefly existed as separate functions on separate cadences (see V076 history) specifically because crossover-detection needed to stay slow, avoiding reaction to noise, while day-cap/max-loss could safely run fast. The state-based decision eliminates that justification: it needs the same every-minute cadence as day-cap/max-loss, since there's no "freshness" concept left to protect. Consolidated back into one `evaluateAutomatedTrading()`, firing once a minute (same `evalSecond`, no five-minute-mark requirement at all now) — one fetch, one set of gates, one fail-closed structure. Verified numerically before consolidating, not just assumed safe: the -2/-3 bars themselves only genuinely change once every five minutes regardless of check frequency, so the faster cadence is strictly a detection-speed improvement, never a change in what's being evaluated.

**The decision itself changed from transition-detection to a state-based check.** Gates, in order: master switch → live-trading-ready → regular trading hours (930-1559, independent of `isLive`'s broader 4am-8pm span) → at least one symbol enabled. Per symbol, day-cap lockout is checked first, before any bar data is even fetched — a held position sells unconditionally, a not-held symbol is skipped entirely, no buying while locked out. Past that: the old rule asked "did a fresh transition just happen" (last bar cleared the deadband, previous bar did not); the new rule asks "does current state match held state" — `last > deadbandPct` means should-own, `last < -getEffectiveNegDeadband()` means should-not-own, with no requirement that this be a new development. A held position sells if it should-not-own *or* fails per-position max-loss against `getEffectiveMaxLossPct()` (checked first, independent of and prioritized over the state-based check, since it's a hard safety threshold on the position's own P&L unrelated to what delta currently reads); a not-held symbol buys if it should-own, the buy window is active, the manual no-buy override isn't active, and buying power (read from the same `accountInfo` already fetched this cycle) covers the invest amount. `prev` is still fetched and logged for diagnostic context but plays no role in the decision at all anymore.

**Why this exists: transition-only detection had a confirmed, recurring blind spot, not a rare edge case.** Three separate missed trades in one real trading day (August 20) — a bar misreading while still forming, settling to its true value a cycle later, but by then already shifted from "current" to "previous," so its own real transition was never evaluated as fresh. The state-based check closes this by not caring when a move started, only whether it's still true right now. Confirmed live on August 21: SMCI was bought by the state-based check directly, matching a real chart showing exactly the established-trend pattern this was built for — a move the old rule could easily have missed entirely if no fresh flip existed at the moment it happened to check.

**The risk this design creates on its own — the state-based check immediately re-buying a position a day-cap lockout just forced closed — was solved before it was ever built.** Worked out over two rounds of user-provided pseudo-code: the first draft only guarded a position already held, leaving a freshly-sold one free to re-buy the instant it read positive again; the second draft fixed it by gating the entire per-symbol block on lockout state first. Verified numerically before shipping: a bar reading green the cycle immediately after a day-cap sell does not trigger a buy-back.

**One genuine, deliberate tradeoff, distinct from the old rule's noise-avoidance, and now the deadband is the only remaining protection against it.** The old design had two layers against chop: the deadband itself, and the fresh-transition requirement. The state-based check removes the second layer entirely — the deadband alone now has to absorb any oscillation around its own boundary. Adjustable live in Settings with immediate effect on the very next cycle, no code change needed, which matters more now than before precisely because it's the only lever left if chop shows up.

**The evaluated bars are still index -2/-3, not -1/-2 — unchanged by the state-based rewrite.** Confirmed directly from the data-fetching code's own comment: the most recent bar in any fetch is *always* still-forming, never settled — not occasionally, but by construction, on both Alpaca and the user's own proxy. `classifyDelta()`/`computePctDeltaSeries()` compute the same percentage-point delta Compare's own chart uses (verified numerically to match the full normalize-then-subtract approach); `classifyDelta()` itself is no longer called from the evaluator at all (the state-based check uses direct numeric comparisons instead), but `buildComboOptions()`'s bar coloring (§5) still uses the same three ranges, so what's visible on the chart still matches what the logic evaluates.

**Deadband override for watch-only symbols (`deadbandOverrideSymbols`/`deadbandOverridePct`)** — deliberately small: one override group, not a general per-symbol system, matching stated real-world experience that one is enough. Chart-display-only, confirmed by tracing every caller of `classifyDelta()` — the actual decision logic is untouched, always reading the single global `deadbandPct` regardless of what's in the override list. Resolved inside `buildComboOptions()` via a new `symbol` parameter, threaded through from Compare and Research (which each show one symbol's own bars) but deliberately not from Trend's composite call, since a blended average across several symbols isn't really "a symbol" the override has a coherent meaning against — Trend simply never passes one, so it's structurally excluded rather than specially filtered. The list's real meaning isn't "symbols needing a different number" — it's "symbols I do not plan to auto-trade" (QQQ/DIA/VOO as index-sentiment gauges being the motivating case), which settled the bolt-toggle question in one move: it stays completely untouched for symbols on this list, no hiding, no gating, since hiding an already-active toggle would remove the one control specifically guaranteed to always work. A small badge (bottom-right of the chart, `pointer-events:none`) shows the actual override value whenever it's active, on both Compare and Research.

**Negative-side deadband and time-of-day max-loss both follow the same "one new optional field, empty means symmetric" shape.** `getEffectiveNegDeadband()` returns `deadbandNegPct` if it's a real number, otherwise falls back to `deadbandPct` — one place the fallback lives, so both the state-based decision and the chart's bar coloring stay in sync by construction. `getEffectiveMaxLossPct()` does the analogous thing for time of day: `maxLossPctMorning` applies only before the fixed, non-adjustable `AUTO_TRADE_MORNING_CUTOFF_HMM` (11:30) and only if it's been explicitly set; otherwise `maxLossPct` applies all day, matching every prior validated session's behavior exactly. Neither function tracks *when* a position was opened — both just check the current gate (deadband sign, wall-clock time) fresh on every call, so a position held across the 11:30 boundary simply starts using the other threshold the instant the clock crosses it, by explicit design rather than oversight.

**Day caps** — evaluated every minute now, using the same `today` figure already shown on the account card (`equity - last_equity`), not a separately-computed number. Crossing either cap sets a sticky, one-way lockout (`dayCapLockoutActive` + a session-keyed timestamp) and sells every bolt-enabled held position individually — not a blanket account-wide liquidate, since manual trading may still be happening alongside the bot during this testing phase, and per-symbol selling can never accidentally catch a manually-held position the bot never touched. The lockout persists through the rest of that trading session regardless of what `today` reads afterward (selling realizes the spread, so the number right after a trigger can land on either side of the threshold that caused it) and resets only when the session key no longer matches the current 4am-anchored session — not at midnight, since Alpaca's own internal reset timing isn't known with confidence. Confirmed live for the first time on August 26 (Max Gain), and manually cleared via the toggle below the same day.

**Max Gain cap ($, 0–10000)** stays a simple positive-magnitude threshold: `todayPL >= maxGainCapDollars`.

**Max Loss/gain-protect cap ($, ±1000, added 2026-08-27/28) is a direct signed threshold, not a magnitude below zero** — `todayPL <= maxLossCapDollars`, no internal negation. A negative value protects against loss, same practical behavior as the old positive-only convention (`-20` locks out at -$20, same as the old `20`); a positive value protects an existing gain instead (`+15` locks out if today's total drops below +$15) — built specifically for re-enabling mid-day via the clear toggle below after Max Gain has already tripped, to guard whatever's already banked rather than only ever limiting fresh downside from zero. Deliberately no auto-migration of an existing saved value on this change — a flipped sign convention silently reinterpreting an old number was judged riskier than a one-time manual re-entry.

**The per-position max-loss check (§12's own `getEffectiveMaxLossPct()` comparison) was moved to run at the same level as the day-cap check — before any bar-series fetch, unconditionally, every cycle — after a real, live-observed miss.** A held position was watched crossing its configured threshold and continuing to fall for several cycles before finally selling. Traced to a genuine structural gap: the check only ever needs `pos.pct` (Alpaca's own position data, already fetched once per cycle for every symbol), never the bar series — but it lived inside the same `try`/`continue` block as the series fetch, which it never actually needed. A symbol whose series fetch failed or came back short on a given cycle had its max-loss check silently skipped too, contradicting the check's own comment claiming it was "independent of the buy window and the master switch" — true, but silently not independent of the series fetch succeeding. Verified numerically against the exact bug scenario (a losing position, a failing series fetch) and three other cases before trusting the fix, confirming no regression to the surrounding decision logic.

**A manual clear for the day-cap lockout — `autoTradeDayCapClearToggle`, added 2026-08-27/28.** Motivated directly by a real limitation: being permanently locked out until the next day, even on a day the user is actively watching and confident about, forced a fallback to fully manual trading with no safety net at all — the worst available option on exactly the day most likely to call for engaged, deliberate action. Deliberately asymmetric, not a real two-way toggle: "On" is disabled in the HTML itself (`disabled`), since only the bot's own day-cap trigger should ever set that state; "Off" is the only genuine, clickable action, and it does exactly one thing — sets `dayCapLockoutActive = false`. No new comparison logic needed at all: the existing evaluator already only re-checks `todayPL` against the caps when the flag is `false`, so clearing it and not actually raising the caps enough means the very next cycle re-locks it automatically, verified numerically across the insufficient-adjustment, sufficient-adjustment, and no-action cases. Shares the exact same `dayCapReallyActive` condition (`isLive` and reason being `"gain"`/`"loss"`, never `"eod"`) as the amber cap-field highlight, computed once and reused by both — a real bug in the toggle's own first draft (checking only the raw flag, missing that shared filtering) is what made this sharing necessary, after the toggle showed "On" in a state the highlight correctly didn't.

**`lossAlertPct` removed entirely as its own stored, editable setting (added 2026-08-27/28).** Previously a completely separate value from the bot's own `maxLossPct`/`maxLossPctMorning` — same conceptual "loss threshold" idea, confirmed via exhaustive search to have zero code path actually connecting the two, despite an early comment in this same section's own history already flagging the exact overlap risk months earlier. Now a live mirror: the Settings field stays visible but read-only, always showing `getEffectiveMaxLossPct()`; the top Positions stat card, each Positions table row, and its TOTAL row all read directly from that same function — one source of truth, structurally unable to drift apart again.

**A visual indicator for the day-cap lockout took two real corrections before landing right, both driven by an actual screenshot rather than caught in advance.** First build: the Settings dialog's "Max gain cap"/"Max loss cap" labels turn amber (the same tone the historical-date label uses) whenever `dayCapLockoutActive` is true — but a real screenshot showed this reading "active" on a Saturday, with neither cap ever having been hit that week. Two separate things were wrong. First: the flag can legitimately still read `true` over a weekend — `getSessionWindow()` correctly treats it as "still Friday's session" until Monday genuinely begins, so the stale-session reset (which only ever fires once the evaluator itself runs) hadn't had a chance to clear it — but nothing is actually being prevented with the market closed, so showing "active" was misleading regardless of the flag's raw value. Fixed by gating the indicator on `isLive` too. Second, and deeper: the same flag gets set by the routine EOD close every single trading day, completely independent of whether either cap was ever crossed — the user's own framing resolved this cleanly: EOD is normal, expected operation, never worth a visual flag, only a genuine gain/loss cap crossing is. A new `dayCapLockoutReason` field (`"gain"`/`"loss"`/`"eod"`) now tracks which of the three actually set the flag, read purely to decide whether to show the indicator — never to display the reason text itself.

**A separate, freely-reversible lockout — `manualNoBuyToday`** — lets the user pre-emptively call a day "done" before anything has traded, on the read that it's likely to be a bad one, and undo that call just as easily if the read turns out wrong. Deliberately not a reuse of `dayCapLockoutActive`: that one is sticky and one-way by design; this one needs to be flippable on and off at will, which is exactly why it's a completely separate flag with its own session-keyed reset, mirroring the day-cap's 4am pattern independently rather than sharing it. Scoped narrowly per explicit instruction — it only ever blocks new buys, checked in the not-held branch alongside the buy-window check; a position already held when the flag is turned on mid-day is completely unaffected, still managed by the normal sell/max-loss/state-based logic with no awareness the flag even exists. A real bug was caught before shipping: the session key has to be set the moment the toggle is saved as "on," not left for the evaluator's own reset check to handle, since that check only ever clears a stale key, it never sets a fresh one — without the fix, saving with the toggle on would leave the key `null`, and the very next cycle would see a mismatch and silently flip the flag back off one cycle later.

**End-of-day sell (15:55)** — a second, independent trigger on the same 1-second timer, deliberately a separate `if`, not `else if`, alongside the normal eval-second trigger. The two defaulting to the same second (59) means an `else-if` would let the normal branch silently win the tie and skip the EOD-specific unconditional sell entirely — caught and fixed before shipping. Pre-sets the lockout flag, then calls the exact same `evaluateAutomatedTrading()` unmodified — no separate sell mechanism, since the per-symbol loop already checks that flag first. Still not exercised live as of August 22 — verified only numerically.

**Console logging** — every gate, every per-symbol decision, so the evaluator's reasoning is fully visible, not just its outcomes. Both the last and previous bar's actual delta value are logged (not just their classification label), added specifically to make a chart-vs-log discrepancy diagnosable without needing to catch the exact moment before the chart's own faster, independent refresh moves on — `prev` is logging/context only now, not part of the decision. The four decision lines (`BOUGHT`/`SOLD`/`no buy`/`no sell`) render as colored `%c` badges for quick scanning — colors picked for basic readability, not held to the same rigor as an actual UI element, since a console message is a developer aid, not something end users see.

**The bolt toggle** (Compare tiles) — three states, all solid/fully-opaque colors, no `opacity` anywhere: off (grey, transparent), armed (`#426284`, enabled but outside the buy window right now), active (`#5C89B9`, enabled and within it). Armed's color is derived from active using the same proportional dimming ratio already established for `--brand`/`--brand-dim`, not picked arbitrarily. Went through several real iterations on the icon color specifically (dark → `--ink` → white) and the armed state's mechanism (originally `opacity:.45`, which reads as a blurry fade rather than a deliberate color) — each correction driven by a real screenshot, including one case where what looked like a rendering bug for two full rounds turned out to be armed working exactly as designed. The toggle click handler is deliberately unconditional — always works regardless of app state — and triggers a one-time `alert()` (not a blocking `confirm()`) when turning off a symbol that's currently held, since the bolt now also controls sell/max-loss monitoring for that position, not just new buying. A real, practical consequence of the state-based check worth being precise about: a symbol's bolt being on at all (regardless of when or why it was turned on) means the bot is watching that symbol continuously — enabling it mid-move on an already-trending symbol gets picked up on the very next cycle, something the old fresh-transition rule structurally could not do.

**The header's own bolt icon** (`#autoTradeChip`, opens the Automated Trading dialog) now mirrors `masterEnabled` the same way the per-symbol bolt mirrors `autoTradeEnabledIds` — solid `#5C89B9` fill with a white icon when the master switch is on, the same plain outlined look as Settings/Help when off. Updated on page load and immediately after the dialog's save handler — the only two places `masterEnabled` can actually change — with no per-tick refresh needed, since unlike the per-symbol armed/active distinction this state isn't time-dependent.

**Account balance and buying power** now display as small blue text (`#5C89B9`) in the stat-card row, sharing the same absolutely-positioned container as the wall clock, opposite side. Reads `equity`/`buyingPower` from the same `accountInfo` `renderAccountRow()` already fetches on its own refresh cadence — no new fetch. Shows `-` for either value in Sample mode, where both are `null` in the underlying data (no plausible value to fabricate the way price drift stands in for a real quote) — the "-" is a display-layer decision, kept separate from the data layer's own `null`.

**Safety, specific to real money:**
- The invest-dollar cap ($5000) is enforced at four independent points referencing one constant (HTML `max`, Settings save-time clamp, restore-from-storage clamp, buy execution's own clamp) — proven numerically that even a value which somehow bypassed the earlier layers still can't slip through the last one, and that a smaller configured value is never forced upward to meet the ceiling.
- Buying power is checked against the invest amount immediately before every buy, reading from the same `accountInfo` already fetched this cycle — no extra network call. Console-only, matching every other decision this evaluator makes (day-cap, max-loss, no-buy) — none of those use a toast/popup either. Fail-closed like everything else here: an unreadable value blocks the buy exactly like a confirmed-insufficient one, not a default-to-proceed — a real correction made mid-build, since the first draft only checked the insufficient case and let an unreadable one silently pass through.
- `TradingAPI.buy()`/`sell()` are called directly from automated logic, never `executeSell()` — that function calls a blocking `confirm()`, which would freeze an unattended page indefinitely waiting for a click that will never come.
- Native browser validation (`checkValidity()`/`reportValidity()`) blocks Save entirely on an out-of-range typed value, showing the real browser tooltip — additive to the existing silent clamps, which still guard the separate path of a value restored from `localStorage` that never touched the dialog.
- Import deliberately forces `masterEnabled` false and clears `autoTradeEnabledIds`/lockout state on any imported settings blob, regardless of what the source device had — export/import predates automated trading and was never built with a second device in mind; without this, importing a workhorse device's settings onto a viewing-only device would silently carry over an armed bot. The numeric configuration (HMM window, invest $, deadband, caps) survives the import untouched, since it's inert without the master switch and useful for a backup or replacement workhorse.
- Manual trading (Buy/Sell/Liquidate) is completely independent of every piece of this — confirmed directly from the code, not assumed — so none of the automated-trading state can ever block or interfere with a manual trade, in either direction.

**Help modal** — a dedicated section, hidden (`display:none`) unless `isLiveTradingReady()` is true at the moment Help is opened, re-checked on every open rather than cached, so the section never describes a feature that couldn't currently do anything.

**Market Watch subtitle** — derived, not a new setting: appends "- PAPER" or "- SAMPLE" based on `dataMode`/whether the account URL contains "paper," computed once at page load only (not re-checked after a Settings save, a deliberate simplification).

**Validated live, with real money, across six-plus trading sessions so far.** August 19: the bot bought (capped at $100) and later sold a position matching the (then-transition-only) crossover logic; a bot-bought position manually added to afterward was still correctly monitored as one blended position. August 20: `evaluateFastRiskChecks()`, the deadband override, and the bar-settling fix were all confirmed working, and the same session surfaced transition-detection's recurring blind spot. August 21: the state-based redesign that fixes that blind spot was confirmed live on its first real trading day, under genuinely difficult market conditions. August 24: the app's first fully unsupervised trading day — no ability to intervene — during a real, scheduled market-moving catalyst (a Treasury Department press conference on new sanctions). Every one of the six actively-traded symbols ended the day negative on raw price (-0.91% to -3.56%), and the account still closed positive: $7.29 realized across 18 round trips (12 wins, 6 losses), independently computed from real Alpaca activity data and matching the user's own reported total. August 25: a deliberate live experiment (-0.3% position-loss threshold, confirmed correct for the morning window) run on a day already expected to go poorly, by design, not by accident. **August 26: Max Gain cap confirmed live for the first time, and cleared via the new manual toggle the same day, both on their very first real-world exercise.** End-of-day sell remains the one mechanism still unexercised live on any date, resting entirely on numerical verification.

**Open, not yet acted on:** whether a single positive/negative deadband is the right model, or whether momentum in each direction is different enough in nature to warrant two separate numbers. Raised for the first time on August 21, explicitly deferred — reasoning about it before real data existed would have been guessing, and the actively-difficult trading day is what's sharpening the intuition worth eventually testing. The mechanism to test it (`deadbandNegPct`) now exists as of 2026-08-22, but no value has been set yet.

## 13. Account Activity Summary

**Built specifically for the scenario §12's own validation just exercised for real: a fully unsupervised trading day, with no console open to watch live, and no way to reconstruct what happened afterward without it.** A round-trip summary table at the bottom of Positions, independent of currently-held positions — it still shows the day's completed activity even after everything's already closed out, which matters precisely because `renderPositions()` itself early-returns "No open positions" in that exact case.

**The pairing logic (`computeActivitySummary()`) was validated twice in Python against real Alpaca account-activity data before a single line of it was ported to JS.** Alpaca's trade-activity rows have no direct field linking a sell back to the buy that opened it — the approach, worked out from the user's own prior experience with this exact problem: combine any rows sharing one `order_id` into a single logical buy/sell event (a partial fill is one decision Alpaca happened to split into multiple rows, not multiple decisions); group by symbol, sort chronologically, pair consecutive buy→sell as one round trip; if a symbol's *first* event for the day is a sell, that's a position opened before the query's date range — an "orphan close," excluded from every summary since its true cost basis isn't knowable from that day's data alone, but counted and surfaced, never silently dropped. This exact "orphan close" case showed up in both validation days (August 21 and August 24) — both times a manually-held QQQ position, kept open overnight deliberately, never the bot's own doing. The JS port was checked against the same real August 24 data used to validate the Python version and produced an identical $7.29 total, 18 round trips, before being trusted.

**The table shows symbol-summary rows, not individual trades** — # Trades, Avg Cost Basis, wins/losses split, Best Win, Worst Loss, Total P&L, Avg P&L/Trade, with a TOTAL row aggregating across symbols, matching the same visual pattern the Positions table already uses for its own TOTAL row. Colors reuse the existing `signClass()`/`signColor()`/`signPrefix()` helpers rather than introducing new logic; Best Win is always green, Worst Loss always red; a symbol with zero trades of either type shows "-", not `$0.00`, since a dash and a real break-even trade are different things. Detail columns (# Trades, Avg Cost Basis, Best Win, Worst Loss, Avg/Trade) are hidden on narrow screens via w3.css's own built-in `w3-hide-small` utility class, already loaded as part of the app's existing stack — no new responsive CSS needed.

**Avg Cost Basis (added 2026-08-25) is per-trade, not a running sum across a symbol's trades** — matches the existing Avg-P&L-per-trade convention, and reads as a single, stable figure (should hold consistent across a symbol's trades on a given day, since Invest $ is one fixed config value) rather than a number that just grows with trade count. Verified against real data: every symbol landed on the same figure, matching that day's actual configured Invest $ exactly. **Deliberately no TOTAL-row equivalent** — surfaced by the user expecting $6000 there (Invest $ × 6 enabled symbols) and getting a different number instead, which traced to a real, worthwhile finding: that figure isn't actually derivable from this table's own data at all. It answers "total capital committed across the whole watchlist," not "what happened today" — a symbol that never traded that day wouldn't appear as a row, so any total computed from this table's own rows would be silently wrong on any day where not every enabled symbol happens to trade. Resolved by leaving the TOTAL cell empty, matching a pattern this table had already established for Best Win/Worst Loss, where the same "no single honest total exists" reasoning already applied.

**Fetches once when the Positions view loads, plus a manual Refresh button** for re-pulling without leaving the view — though this took a second real bug to actually achieve. `renderActivitySummary()` was originally called unconditionally from inside `renderPositions()`, which is itself called directly by the account-refresh timer every 15 seconds — bypassing view-switch logic entirely, so the section was silently re-fetching from Alpaca and rebuilding its DOM on every timer tick while the user simply sat on the view, not just on genuine view-load or an explicit Refresh click as intended. Fixed with an `activitySummaryNeedsLoad` flag, true only on a genuine view-load or an explicit Refresh click, false everywhere else — verified numerically across the full scenario (repeated timer ticks while staying put, a manual refresh, and switching away and back), landing on exactly the 3 real fetches that should happen out of many possible trigger points.

**A real, structural bug was caught and fixed before this ever worked at all — via the user's own live screenshot, not by review.** The new panel's content was almost certainly rendering correctly the whole time; the actual problem was that it was permanently invisible. The page's `render()` function hides every `.view-panel` element, then shows only the one exact match for the current view (`currentView + "Panel"`) — since the new section was a *second* `.view-panel` for the same "positions" view, it got hidden by that generic loop and never shown again, regardless of what its `innerHTML` actually contained. Fixed by removing it from that class entirely and controlling its visibility explicitly, alongside the main toggle, rather than through the generic one-panel-per-view mechanism that was never built to expect two panels for the same view. A second, smaller mistake in the same build: a CSS class (`btn-secondary`) was referenced for the Refresh button without ever confirming it existed anywhere in the app — it didn't. Caught by explicitly searching for every real button class before trusting the assumption; fixed by reusing the existing `.btn-cancel` styling instead, the closest real match for a low-stakes secondary action.

**Pagination is implemented (2026-08-25), not just researched.** Matches the confirmed Alpaca convention exactly — genuinely different from the bars/series endpoint pattern the user's own older reference code was written against: there's no `next_page_token` field on the response at all, since the response is a plain array; the *last item's own `id`* becomes the `page_token` for the next request, looping until a page returns fewer than `page_size` (100) rows. A 20-page hard safety ceiling (2000 rows) guards against a runaway loop rather than trusting the termination condition alone, and a brief 250ms courtesy pause sits between pages, matching the spirit of the user's own older reference code's own pagination delay. Verified numerically across four scenarios before being trusted: correct multi-page collection with accurate token extraction on each page, no wasted extra fetch on the common single-page case, the safety limit correctly capping a runaway scenario, and proper URL-encoding of the `::` character present in real Alpaca activity IDs.

## 14. Account View (Daily Gains Chart)

**A bar (daily P&L) + area (cumulative) combo chart, one bar per trading day, matching the app's existing dark-theme visual language rather than introducing a new look.** Built with static, hand-picked sample data first specifically to iterate on look and feel before touching real data — deliberately not seeded/randomized like the app's other sample generators, since the goal was a stable, repeatable dataset to design against, not simulated variability. Two y-axes, since cumulative naturally grows to a different scale than any single day's bar — sharing one axis would flatten whichever series has the smaller range.

**Cumulative P&L, not equity, drives the second series** — a deliberate choice informed by the user's own prior experience building a similar chart before (possibly in a different tool), where equity was tried and rejected: too flat relative to daily swings to be visually useful, since a day's few-hundred-dollar move barely registers against tens of thousands in total equity.

**`DataSource.loadPortfolioHistory()`** — Alpaca's `/v2/account/portfolio/history` endpoint, adapted from the user's own `account.js` `history()` reference. Same endpoint, same `pnl_reset=per_day` (the parameter that makes each day's figure genuinely independent, not a slice of a running cumulative total since the query period started) — but returns `{date: epoch ms, pnl}` pairs matching what the chart-options builder already expects, rather than the reference's own `{t, net, pnl, pnl_pct}` shape, and only `pnl` is used at all.

**Dates built via explicit local `Date(year, month, day)` construction, in both the sample data and the real fetch, not bare ISO strings.** A bare date string like `"2026-08-11"` parses as UTC midnight, which can silently display as the wrong calendar day once rendered in a negative-UTC-offset timezone (e.g. US Eastern) — the exact same class of timezone pitfall this app has been careful about elsewhere (`effectiveToday()`, `getSessionWindow()`). Real Alpaca timestamps (epoch seconds → ms) are inherently unambiguous already; the explicit local construction specifically protects the sample-data path and any date-string handling from the same risk.

**`accountMinStartDate`** — optional Settings field, clips pre-bot history (e.g. the user's own manual-trading years, or an older app) out of the chart. Applied as the *later* (more recent) of this setting and `(today - 14 days)` — can only ever narrow the requested 14-day window, never extend past it; an older-than-14-days value is silently ignored rather than pulling in more history than was actually requested. 14 days chosen deliberately, not arbitrarily — more days was judged too busy/dense to read at a glance, defeating the purpose of a chart meant for a quick daily check.

**`accountDailyTargetDollars`** — optional Settings field, draws a flat, dashed reference line on the daily-gains axis specifically (not the cumulative one) at the configured dollar figure, labeled with the value. A flat dollar figure, deliberately not derived from any %/capital-base calculation — capital varies too much day to day (Invest $ alone has ranged from $100 to $1000 across real sessions) for one "correct" base to convert a percent target against. Purely visual, never read by any trading decision — same "reference, not trade decisions" philosophy as the chart as a whole. Reused later, unchanged, as the source for the Today card's own goal-based percentage (§ automated trading section above) — one setting, two display purposes, deliberately kept distinct in scope from the bot's own Max Gain cap.

**Both Settings fields require a page reload to actually take effect, not just a view switch** — the Account view's own re-render is gated by the same `currentSignature()`-based caching every other view uses, which doesn't include either of these settings as an input, so simply navigating away and back doesn't reliably force a fresh read of a just-changed value. Documented directly in each field's own label ("refresh page after save") rather than fixed at the code level, since both are expected to be rarely-changed, set-once values.

**A manual Refresh button, added after deliberately deferring both a caching fix and a 4am auto-refresh** — the user explicitly judged the manual button sufficient on its own, rather than building either of the other two. Making the view's header (title context + button) rebuild unconditionally, so it stays present even on error/empty-data paths matching the activity-summary's own established pattern, introduced a real regression: the panel's `innerHTML` now got wiped on every single call, including ordinary successful re-renders, but the module-level ApexCharts instance variable wasn't being reset to match — so a second call (like clicking Refresh) would try to `updateOptions()` on an orphaned instance no longer attached to any visible DOM element, silently failing to render anything. Same failure shape already caught once before on this exact chart's own error/empty paths, reintroduced by a different change — closed with a single unconditional `destroy()` at the very top of the function, which also allowed the now-redundant destroy calls further down to be removed. Verified numerically across three consecutive simulated calls (including two simulated Refresh clicks) — a genuinely fresh instance created every time, never an orphaned update attempt.

**Not yet exercised live long enough to validate the chart's own visual design against real, varied data** — confirmed working correctly against real account data on the days it's been checked, but the real account doesn't yet have enough day-to-day variety (a real mix of large wins, large losses, and flat stretches) to have properly stress-tested the chart's look and feel the way the original static sample dataset was built to allow.
