# Uptick — Code Summary

A single-file HTML app (`uptick-demo.html`) — everything below lives in one `<script>` tag, in the order it's described here.

## Latest insight — V082 — August 24, 2026

**The single most important thing this session proved: the app survived its first fully unsupervised trading day, with no ability to intervene, during a scheduled, market-moving catalyst.** Every prior live session had the user actively watching, able to step in if something went wrong — that safety net was never actually needed, but it was always there. Today it wasn't. A real, scheduled event (a Treasury Department press conference on new Iran sanctions) hit mid-morning, and the only response available was whatever the mechanical rules did on their own.

**Deliberately conservative settings matched the actual risk of the day, not a fixed default.** Invest $ stayed at $100 per symbol — nowhere near the $5000 ceiling raised a few sessions ago — specifically because a big, fast, event-driven move is exactly the kind that can reverse just as fast, and today removed the one thing (the user's own judgment on timing an exit) that had made a similar large swing profitable in a past manual trade. Day caps were set tight ($20 gain / $10 loss — confirmed as roughly 1.67% of the day's $600 total exposure, not quite the intended 1%, but close and deliberately conservative either way), and the buy window's start was pushed to 10:00 specifically to avoid entering fresh positions into the announcement's own immediate reaction window. None of this touched selling, which — as established weeks earlier — is deliberately unbounded by the buy window, since a held position needs an exit at any time the market's open.

**The result: every one of the six actively-traded symbols ended the day negative on raw price (-0.91% to -3.56%), and the account still ended up positive.** Independently computed from real Alpaca activity data, using the same round-trip pairing pipeline validated against Friday's session: **$7.29 realized gain across 18 round trips (12 wins, 6 losses)** — a close, honest match to the user's own reported $6.99 (the small difference fully explained by a separate, unrelated overnight QQQ position closing the same day, bringing the account's total movement to -$0.60 starting deficit + $6.99 gained = the reported total). Expressed as a return, $7.29/$600 = **1.215%**, against the Nasdaq's own **-0.79%** the same day — a real, meaningful gap, though the user themselves flagged the honest caveat worth recording: the index's daily % is close-to-close, absorbing whatever happened in the overnight gap, while the bot's return is purely intra-day, so the two numbers aren't a clean apples-to-apples comparison without that context.

**QQQ's "orphan close" pattern — a sell with no matching buy anywhere in that day's activity data — showed up again today, confirming it as a real, recurring, understood case rather than a one-off.** Both times now (Friday and today) it's been the same thing: a position opened before the query's date window, in this instance a manually-held position deliberately kept open overnight specifically to have something to watch when charts otherwise go quiet during closed hours — never the bot's own doing, since its own EOD logic force-closes everything by 15:55 every trading day.

**A real, structural bug was caught and fixed in the new account-activity feature (see §13) before it ever worked correctly, via the user's own live screenshot rather than by review.** The new panel's content was likely rendering correctly the whole time — the actual bug was that it was permanently invisible, hidden by the page's own generic view-switching logic, which shows exactly one panel per view by exact ID match. A second `.view-panel` element for the same "positions" view got caught by that same logic and never shown again, regardless of its content. Fixed by removing it from the generic toggle mechanism and controlling its visibility explicitly instead. A second, smaller mistake in the same build: a CSS class (`btn-secondary`) was referenced without ever confirming it existed — it didn't, anywhere in the app — caught by explicitly searching for every real button class before trusting the assumption, and fixed by reusing the existing `.btn-cancel` styling instead.

**The reconciliation → state-based rename was completed across every user-visible and code-comment location** (Help text, the console log's own reason string, code comments, and this document's own current section) — deliberately **not** applied to this document's History section, matching its own established "never edited, only appended to" rule; those entries describe what was actually said and thought at the time, not retroactively updated terminology. One genuinely unrelated use of the word "reconciling" (about merging two unrelated config fields) was correctly identified and left untouched throughout.

**Alpaca's account-activities pagination was researched and confirmed, though not yet built (still on the list as its own item).** Genuinely different from the bars-endpoint pattern the user's own old reference code used: no `next_page_token` field on the response at all — the response is a plain array, and the *last item's own `id`* becomes the `page_token` for the next request. Worth having settled precisely before ever writing the actual fetch loop.

**One incidental but useful confirmation today: exporting/downloading a file does not count against Claude Desktop's 100-image-per-conversation limit** — verified directly by exporting the working file and confirming the counter didn't move. Only uploaded images/PDF pages count. Relevant given this conversation is approaching that limit and a full handover to a new conversation is planned.

**The deeper throughline surfaced today, worth recording explicitly since it explains why so much of this app is built the way it is:** the 0.75%/day target isn't a hopeful guess — it's the actual, achieved average from the user's own real, sustained *manual* trading over many weeks with a prior version of this app. The "bad days" in that manual history were evidence of ordinary human inconsistency (missing a boring trade, over-reacting to a loud one), not evidence the underlying strategy tops out lower. The bot's job was never framed as being smarter than the user's own good days — only as not having the user's bad ones. And the actual goal is income, not compounding: gains are drawn out monthly against real bills rather than reinvested, which means the simple, non-compounded version of the daily-average math is the honest one for this specific plan, not an understatement of it. Every safety-first design decision across this whole project — the tight day-loss caps, never holding overnight, the manual no-buy override — is load-bearing for that reliability goal, not caution for its own sake.

## 1. Config & State

**`CONFIG`** — the one object holding every setting: `dataMode` ("sample" | "api"), symbol/account API URLs and credentials, `smaPeriod`, `lossAlertPct` (default -0.5, drives three separate hue treatments from one value), two independent refresh rates (`chartRefreshSeconds`, `accountRefreshSeconds`), and `autoTrading` (full detail in §12).

**Top-level state variables**:
- `TICKERS` / `selectedTickerIds` — the watchlist roster and which of them are checked
- `tickerPresets` — named snapshots of `selectedTickerIds` ("symbol groups")
- `currentTf` / `currentView` / `displayWindow` — Timeframe, active view (`trend` | `compare` | `table` | `research` | `positions`), and the "Today" hour-window slice
- `selectedDate` — a picked historical date, or `null` for live ("pretend this day is today")
- `researchSymbol` — the Research view's currently-applied search
- `heldPositions` — `Map<symbol, {dollar, pct, costBasis, currentPrice}>` from the live positions array (fixed, non-moving stub for 3 tickers in Sample mode)
- `autoTradeEnabledIds` — which tickers are bolt-enabled for automated trading, same `Set` pattern as `selectedTickerIds` (§12)
- `controlsExpanded` / `statsRowExpanded` — the two collapsible accordions, now persisted (a real preference reversal after real iPad use — always-expanded-on-load turned out to be more friction than the original "don't confuse a later session" concern was worth)
- `seriesCache` / `viewSignatures` / `viewMeta` — caching layers, covered in §7
- `selectedDateSetAt` — timestamp of when `selectedDate` was last set to a real date, distinct from `lastActivityTime` (which updates on any click at all) — drives a 4am trading-day-boundary reset alongside the existing 60-minute inactivity one (§8)

**Persistence** (`loadSettings()` / `saveSettings()`): everything above except `selectedDate` and `researchSymbol` gets written to one `localStorage` key (`uptick-settings-v1`) as a single JSON blob. Import deliberately overrides parts of this blob before it's ever written — see §12's safety notes.

## 2. Date & Session Logic

**`effectiveToday()`** — the single choke point every date function routes through: returns `selectedDate` if picked, otherwise the real current moment.

**`mostRecentTradingDay()` / `previousTradingDay()` / `tradingDayNDaysAgo(days)`** — weekday-aware date walking for the daily-bar windows (10D/30D/90D/180D), anchored through `effectiveToday()`.

**`getSessionWindow()`** — simulates a real trading session (4:00 AM–8:00 PM), holding at the last completed session outside that window. Returns `{sessionStart, sessionEnd, sessionNow, isLive}`. When `selectedDate` is set, always returns `isLive: false` — one flag disabling Buy/Sell, pausing chart auto-refresh, and hiding the held-position dot, all from a single source.

**`getSeriesWindow(tf)`** — computes fetch boundaries: `wideStart` (extra lookback so SMA has real history) and `displayStart` (the actual shown boundary).

**`trimToDisplayWindow()`** — trims `times`/`close`/`sma` together once SMA is computed on the wider set.

**`applyDisplayWindow(data, windowKey, tf)`** — "Full Day" / "9:00–4:30" / "Last 6H." Anchors to the data's own last timestamp, not `getSessionWindow()` — self-contained, and future-proofed for eventual historical-day browsing.

---

## 3. Sample Data Generator

**`generateSample(symbol, tf)`** — synthetic data, seeded (`mulberry32` + `hashStr`) so the same symbol+timeframe always generates the same shape, with a small live-tick jitter on the last bar while `isLive`.

**`sma(values, period)`** — before the window is full, each point defaults to its own close, so `close − SMA` is exactly 0 during warm-up.

## 4. DataSource, TradingAPI & Account

**`DataSource.loadSeries(symbol, tf)`** — branches on `CONFIG.dataMode`, then on `CONFIG.api.activeSymbolSource` in Live mode:
- **Source A** (your own proxy) — path-based URL, no auth. Optionally appends `?token=` from `CONFIG.api.symbolToken` if set — security through obscurity, not real access control; the backend already reads the parameter but ignores it until populated with something checked server-side against an allowlist. Never appended to Source B.
- **Source B** (Alpaca directly) — a genuinely different request shape: query-string params (`symbols`, `timeframe`, `start`, `end`, `feed=iex`, `limit=5000`, `sort=asc`), account credentials reused as auth headers (not a separate symbol-data credential), base URL defaults to Alpaca's real endpoint but is overridable via the same Settings field for a future version bump.

Both paths coerce `close` to `Number()` and normalize the last intraday bar's timestamp to a clean 5-minute boundary. Cached in `seriesCache`, keyed on `symbol|tf|selectedDate`.

**`DataSource.loadAccountInfo()`** — Live mode fetches `/v2/account` + `/v2/positions` in parallel, populates `heldPositions`, returns `combineAccountAndPositions()`'s dollar-weighted aggregate — now including `equity` and `buyingPower`, both read directly from the same `/v2/account` response already being fetched here, no additional network call for either. Sample mode's equivalent returns `null` for both — no plausible value to fabricate the way price drift stands in for a real quote elsewhere, so the display layer shows "-" for either.

**`TradingAPI`** — `buy()`, `sell()`, `liquidateAll()`.

**`executeSell(symbol, btn)`** — shared by Compare's sell buttons (id-based) and the Positions table's sell buttons (symbol-based directly, since a held position isn't guaranteed to be in the configured watchlist). Awaits `renderAccountRow()` internally so `heldPositions` is guaranteed fresh by the time it returns.

## 5. Chart Building

**`buildComboOptions(...)`** — builds every chart's ApexCharts config. 3 series (delta bars, Close, SMA), 2 y-axes. Delta bar padding is minimal (`maxAbsDelta * 1.04`) so the tallest bar nearly fills the available height. Bar coloring is three ranges, not two — green/neutral/red, split at `±CONFIG.autoTrading.deadbandPct` — matching exactly what the automated-trading logic (§12) evaluates, on every chart using this shared function (Trend, Compare, Research alike), not just where the bolt toggle lives. Originally a hard `delta >= 0` split with no neutral zone; changed after a real, confirmed gap between what the chart showed and what the logic actually saw.

**`marketSessionAnnotations()`** — dashed pink lines at Open (9:30)/Close (4:00).

**`hourlyAnnotations()`** — solid, light-grey, unlabeled lines at 10am–3pm specifically (deliberately excluding 9/16, already marked by Open/Close). A template for a possible future third annotation tier at specific, non-hourly times.

## 6. Views

Five views, one shared title/stat-row area:

- **`renderTrend()`** — Combined. Averages each selected ticker's own % change and SMA into one composite line.
- **`renderCompare()`** — one tile per ticker: chart, symbol color, held-position dot + $/% gain (live-only), Buy/Sell, and the automated-trading bolt toggle (§12) — three solid, fully-opaque states (off/armed/active), no `opacity` transparency anywhere.
- **`renderTable()`** — start/end/delta for the current window.
- **`renderResearch()`** — one-off symbol lookup, separate from the watchlist.
- **`renderPositions()`** — actual open positions, independent of ticker selection/timeframe/window. Symbol, $ Change, % Change, Cost Basis, Sell — reordered and Current Price dropped from display per explicit request ("not useful, just focused on making money"), though the field stays in the underlying data. A blue bolt icon prefixes the Symbol cell when that position's ticker is currently bolt-enabled — a read-only indicator, no click handler, reusing `autoTradeEnabledIds` directly rather than any new state; correctly resolves to false for a held symbol outside the watchlist entirely. Loss-alert hue applies per-row and on TOTAL independently — a single bad position doesn't get masked by an otherwise-fine total, and vice versa. Bypasses the view-signature cache entirely (cheap to rebuild; depends on data that updates on its own refresh cadence, not anything the cache key tracks).

**`render()`** dispatches on `currentView` via `currentSignature()`, and mutes whichever controls don't apply: ticker chips + symbol groups on Research and Positions; timeframe bar + window bar on Positions only.

## 7. Caching Layers (two, deliberately separate)

- **`seriesCache`** — raw fetched/generated data, keyed on `symbol|tf|date`.
- **`viewSignatures` / `viewMeta`** — per-view "have my inputs changed" tracking.

Two different real bugs came from each of these independently, at different points in the project: `seriesCache` missing the date component let a picked historical date silently return stale live data; `viewSignatures` not including `selectedDate` meant the view didn't know to re-render at all. Fixing one never implied the other was already correct.

## 8. Symbol Groups, Watchlist Management & the Historical Date Picker

**`renderTickerPresetRow()`** — a preset is a named snapshot of `selectedTickerIds`, never a separate ticker list. Saving under an existing name updates it *in place* now (fixed today — was previously removing-then-appending, silently moving the group to the end of the row). Muted whenever Research or Positions is active.

**`renderTickerManageList()`** — add/remove/reorder the watchlist roster via a staged `draftTickers` array. Reordering is up/down arrows, not drag-and-drop.

**The historical date picker** (`selectedDate`) — calendar icon on the Today button, its own click zone. Picking a date applies to whatever timeframe is already active. Picking today's actual date collapses back to `null` rather than staying a technically-non-null "historical" state. Two independent resets converge on the same `resetSelectedDateToLive()` helper: the existing 60-minute click-based inactivity timer, and a newer 4am trading-day-boundary check — added after tracing a real, previously-unnoticed risk: `getSessionWindow()` returns `isLive: false` whenever a historical date is picked, and the evaluator's own timer trigger requires `isLive` to fire at all, so a historical date left selected doesn't just pause new buys, it silently stops sell/max-loss monitoring on anything already held. The 4am check specifically catches what inactivity alone couldn't — a date left selected overnight while the app stays genuinely active on other things, so 60 minutes of idle time never accumulates. The Today button's own label turns the same amber used for the day-cap indicator (§12) whenever a historical date is active, with a tooltip spelling out the real consequence — visibility only, no new restriction, since the underlying behavior was already safe by design.

## 9. Auto-Refresh

Two independent wall-clock-aligned timers (`second % rate === 0`, checked on a plain 1-second tick):

- **Chart refresh** — gated on `getSessionWindow().isLive`.
- **Account refresh** — *not* gated on `isLive`. Runs 24/7.
- **Automated trading evaluation** (§12) — a third, separate condition on the same 1-second tick, firing once a minute (no five-minute-mark requirement, since the state-based decision removed the reason that requirement existed), requiring `isLive` and gating on regular hours internally. A fourth, independent `if` (deliberately not `else if` — see §12) handles the 15:55 end-of-day trigger. A brief third trigger existed for one day (August 20) when day-cap/max-loss ran on their own separate, faster cadence via `evaluateFastRiskChecks()` — removed when the state-based redesign consolidated everything back into one function on one cadence (see §12, V076 history).

A separate 200ms interval (`updateRefreshBar`) animates the countdown bar, and also drives the five-minute checkpoint highlight on the Today card (`.five-min-active` — steady, not pulsing, deliberately, so the cue meant to reduce reactive decisions doesn't become a source of it itself). This cue now requires regular trading hours specifically (930-1559), not just `isLive`'s broader 4am-8pm span — narrowed on request, since it was being read as "the bot could be active right now," which stopped being accurate once the bot's own execution got a separate, additional hours gate. `isLive` itself is untouched; only the cue's own display condition and the evaluator's execution gate were narrowed, each independently, sharing one set of constants rather than two that could drift apart.

A related concern was raised and investigated, then closed without a code change: whether switching the UI's own timeframe view (`currentTf`) while the bot trades could feed the evaluator wrong data. Traced directly rather than assumed either way — the evaluator's own series fetch is hardcoded to the literal string `"today"`, never reads `currentTf` at all, so the two are already fully decoupled.

## 10. Formatting & Sign Handling

**`round2(v)`** (`Math.round(v * 100) / 100`) — every display-facing rounded number in the app routes through this first, rather than trusting `toFixed()`'s own rounding, which can disagree with "round half up" on exact half-cent boundaries.

**`signOf(v)` / `signColor(v)` / `signPrefix(v)` / `signClass(v)` / `upDownNeutral(v)`** — determine up/down/neutral coloring based on the *rounded* value, not the raw one. Added today after finding a raw value like `-0.001` would display as `"0.00"` while still coloring red, since the color decision used the un-rounded number. All 16 sites in the app that made this kind of sign-based decision — stat cards, Compare tile color/gain, Table view, Research stats, Positions rows/TOTAL — now route through these instead of each doing its own `>= 0` check. `upDownNeutral()` specifically preserves `null` ("no data yet," e.g. CHANGE before a second update) as genuinely distinct from `"neutral"` (rounds to exactly zero) — collapsing those two would have been a regression, not a fix.

## 11. Misc

**`updatePageTitle(todayPL)`** — sets the browser tab title to `Uptick | ±$N | YYYY-MM-DD_HHMM`, piggybacked on the account refresh cadence. Exists so the browser's own Print/Save dialog — which defaults to suggesting the page title as the filename — becomes a free "auto-name my printed daily record" feature, mirroring a pattern from the user's other apps. Uses local date components (`getFullYear()`/`getMonth()`/`getDate()`) consistently with the already-local time components, after an initial version mixed in UTC-based `toISOString()` for the date half and produced tomorrow's date next to today's actual local time in the evening.

**`lockPageScroll()` / `unlockPageScroll()`** — `position:fixed` + saved scroll offset for modals, needed since `overflow:hidden` alone isn't reliable in Chrome.

## 12. Automated Trading

**`CONFIG.autoTrading`** — `masterEnabled` (default false, local to this device only — export/import forces it off on import, see below), `startHmm`/`endHmm` (buy-only window, default 930/1559, three-layer clamped: HTML `min`/`max`, save-time, restore-time), `investDollars` (default 100, hardcoded ceiling of 5000 — see below), `evalSecond` (default 59), `maxLossPct` (per-position, default -1, the afternoon/all-day default), `maxLossPctMorning` (`NaN` by default, meaning "same as `maxLossPct`" — an explicit value applies only before the fixed 11:30 cutoff), `deadbandPct` (default 0.25, percentage points either side of zero counted as neutral), `deadbandNegPct` (`NaN` by default, meaning "same as `deadbandPct`" — an explicit value gives the negative side its own threshold), `deadbandOverrideSymbols`/`deadbandOverridePct` (chart-display-only override for a small, deliberately single group of "watch, never auto-trade" symbols — see below), `maxGainCapDollars`/`maxLossCapDollars` (account-level day caps, default 100 each, range-clamped 0-10000/0-1000 respectively, input step 5 — loosened from step 10 on 2026-08-24, since the original increment only made sense assuming exactly $100/symbol, an assumption the $5000 ceiling raise had already outgrown), `dayCapLockoutActive`/`dayCapLockoutSessionKey` (sticky lockout state, not user-editable), `dayCapLockoutReason` (`"gain"`/`"loss"`/`"eod"`/`null` — tracks *why* the lockout flag is set, purely to decide whether the UI shows an indicator, never to display the reason itself), `manualNoBuyToday`/`manualNoBuyTodaySessionKey` (a separate, freely-reversible lockout the user can toggle on and off directly — see below), `trailingPct` (disabled field, stays `NaN`). `autoTradeEnabledIds` is a separate top-level `Set`, same pattern as `selectedTickerIds`, persisted independently.

**Hardcoded constants** (declared early, alongside `controlsExpanded`, specifically to avoid the temporal-dead-zone `applySavedSettings()` IIFE would otherwise hit reading a `const` declared later in the file): `AUTO_TRADE_MAX_INVEST_DOLLARS` (5000 — raised 100→150 on 2026-08-21 when sub-$100 orders weren't reliably filling, then 150→5000 on 2026-08-22 once the state-based redesign held up on a genuinely difficult live trading day; referenced by every enforcement point, not settings-editable — raising it further means changing this constant directly, never a UI toggle), `AUTO_TRADE_EOD_HMM`/`AUTO_TRADE_EOD_SECOND` (1555/59), `AUTO_TRADE_REGULAR_HOURS_START`/`_END` (930/1559, shared by the evaluator's own execution gate and the blue five-minute cue's display condition — one source of truth so the two can't drift apart), `AUTO_TRADE_MORNING_CUTOFF_HMM` (1130, fixed and not settings-editable, per explicit instruction — only two windows, not adjustable), `AUTOTRADE_LOG_GREEN`/`_RED`/`_GREY` (console `%c` badge styles for the four decision-outcome log lines).

**One function again, not two — the state-based redesign removed the reason they were ever split.** `evaluateFastRiskChecks()` and `evaluateAutomatedTrading()` briefly existed as separate functions on separate cadences (see V076 history) specifically because crossover-detection needed to stay slow, avoiding reaction to noise, while day-cap/max-loss could safely run fast. The state-based decision eliminates that justification: it needs the same every-minute cadence as day-cap/max-loss, since there's no "freshness" concept left to protect. Consolidated back into one `evaluateAutomatedTrading()`, firing once a minute (same `evalSecond`, no five-minute-mark requirement at all now) — one fetch, one set of gates, one fail-closed structure. Verified numerically before consolidating, not just assumed safe: the -2/-3 bars themselves only genuinely change once every five minutes regardless of check frequency, so the faster cadence is strictly a detection-speed improvement, never a change in what's being evaluated.

**The decision itself changed from transition-detection to a state-based check.** Gates, in order: master switch → live-trading-ready → regular trading hours (930-1559, independent of `isLive`'s broader 4am-8pm span) → at least one symbol enabled. Per symbol, day-cap lockout is checked first, before any bar data is even fetched — a held position sells unconditionally, a not-held symbol is skipped entirely, no buying while locked out. Past that: the old rule asked "did a fresh transition just happen" (last bar cleared the deadband, previous bar did not); the new rule asks "does current state match held state" — `last > deadbandPct` means should-own, `last < -getEffectiveNegDeadband()` means should-not-own, with no requirement that this be a new development. A held position sells if it should-not-own *or* fails per-position max-loss against `getEffectiveMaxLossPct()` (checked first, independent of and prioritized over the state-based check, since it's a hard safety threshold on the position's own P&L unrelated to what delta currently reads); a not-held symbol buys if it should-own, the buy window is active, the manual no-buy override isn't active, and buying power (read from the same `accountInfo` already fetched this cycle) covers the invest amount. `prev` is still fetched and logged for diagnostic context but plays no role in the decision at all anymore.

**Why this exists: transition-only detection had a confirmed, recurring blind spot, not a rare edge case.** Three separate missed trades in one real trading day (August 20) — a bar misreading while still forming, settling to its true value a cycle later, but by then already shifted from "current" to "previous," so its own real transition was never evaluated as fresh. The state-based check closes this by not caring when a move started, only whether it's still true right now. Confirmed live on August 21: SMCI was bought by the state-based check directly, matching a real chart showing exactly the established-trend pattern this was built for — a move the old rule could easily have missed entirely if no fresh flip existed at the moment it happened to check.

**The risk this design creates on its own — the state-based check immediately re-buying a position a day-cap lockout just forced closed — was solved before it was ever built.** Worked out over two rounds of user-provided pseudo-code: the first draft only guarded a position already held, leaving a freshly-sold one free to re-buy the instant it read positive again; the second draft fixed it by gating the entire per-symbol block on lockout state first. Verified numerically before shipping: a bar reading green the cycle immediately after a day-cap sell does not trigger a buy-back.

**One genuine, deliberate tradeoff, distinct from the old rule's noise-avoidance, and now the deadband is the only remaining protection against it.** The old design had two layers against chop: the deadband itself, and the fresh-transition requirement. The state-based check removes the second layer entirely — the deadband alone now has to absorb any oscillation around its own boundary. Adjustable live in Settings with immediate effect on the very next cycle, no code change needed, which matters more now than before precisely because it's the only lever left if chop shows up.

**The evaluated bars are still index -2/-3, not -1/-2 — unchanged by the state-based rewrite.** Confirmed directly from the data-fetching code's own comment: the most recent bar in any fetch is *always* still-forming, never settled — not occasionally, but by construction, on both Alpaca and the user's own proxy. `classifyDelta()`/`computePctDeltaSeries()` compute the same percentage-point delta Compare's own chart uses (verified numerically to match the full normalize-then-subtract approach); `classifyDelta()` itself is no longer called from the evaluator at all (the state-based check uses direct numeric comparisons instead), but `buildComboOptions()`'s bar coloring (§5) still uses the same three ranges, so what's visible on the chart still matches what the logic evaluates.

**Deadband override for watch-only symbols (`deadbandOverrideSymbols`/`deadbandOverridePct`)** — deliberately small: one override group, not a general per-symbol system, matching stated real-world experience that one is enough. Chart-display-only, confirmed by tracing every caller of `classifyDelta()` — the actual decision logic is untouched, always reading the single global `deadbandPct` regardless of what's in the override list. Resolved inside `buildComboOptions()` via a new `symbol` parameter, threaded through from Compare and Research (which each show one symbol's own bars) but deliberately not from Trend's composite call, since a blended average across several symbols isn't really "a symbol" the override has a coherent meaning against — Trend simply never passes one, so it's structurally excluded rather than specially filtered. The list's real meaning isn't "symbols needing a different number" — it's "symbols I do not plan to auto-trade" (QQQ/DIA/VOO as index-sentiment gauges being the motivating case), which settled the bolt-toggle question in one move: it stays completely untouched for symbols on this list, no hiding, no gating, since hiding an already-active toggle would remove the one control specifically guaranteed to always work. A small badge (bottom-right of the chart, `pointer-events:none`) shows the actual override value whenever it's active, on both Compare and Research.

**Negative-side deadband and time-of-day max-loss both follow the same "one new optional field, empty means symmetric" shape.** `getEffectiveNegDeadband()` returns `deadbandNegPct` if it's a real number, otherwise falls back to `deadbandPct` — one place the fallback lives, so both the state-based decision and the chart's bar coloring stay in sync by construction. `getEffectiveMaxLossPct()` does the analogous thing for time of day: `maxLossPctMorning` applies only before the fixed, non-adjustable `AUTO_TRADE_MORNING_CUTOFF_HMM` (11:30) and only if it's been explicitly set; otherwise `maxLossPct` applies all day, matching every prior validated session's behavior exactly. Neither function tracks *when* a position was opened — both just check the current gate (deadband sign, wall-clock time) fresh on every call, so a position held across the 11:30 boundary simply starts using the other threshold the instant the clock crosses it, by explicit design rather than oversight.

**Day caps** — evaluated every minute now, using the same `today` figure already shown on the account card (`equity - last_equity`), not a separately-computed number. Crossing either cap sets a sticky, one-way lockout (`dayCapLockoutActive` + a session-keyed timestamp) and sells every bolt-enabled held position individually — not a blanket account-wide liquidate, since manual trading may still be happening alongside the bot during this testing phase, and per-symbol selling can never accidentally catch a manually-held position the bot never touched. ## 13. Account Activity Summary

**Built specifically for the scenario §12's own validation just exercised for real: a fully unsupervised trading day, with no console open to watch live, and no way to reconstruct what happened afterward without it.** A round-trip summary table at the bottom of Positions, independent of currently-held positions — it still shows the day's completed activity even after everything's already closed out, which matters precisely because `renderPositions()` itself early-returns "No open positions" in that exact case.

**The pairing logic (`computeActivitySummary()`) was validated twice in Python against real Alpaca account-activity data before a single line of it was ported to JS.** Alpaca's trade-activity rows have no direct field linking a sell back to the buy that opened it — the approach, worked out from the user's own prior experience with this exact problem: combine any rows sharing one `order_id` into a single logical buy/sell event (a partial fill is one decision Alpaca happened to split into multiple rows, not multiple decisions); group by symbol, sort chronologically, pair consecutive buy→sell as one round trip; if a symbol's *first* event for the day is a sell, that's a position opened before the query's date range — an "orphan close," excluded from every summary since its true cost basis isn't knowable from that day's data alone, but counted and surfaced, never silently dropped. This exact "orphan close" case showed up in both validation days (August 21 and August 24) — both times a manually-held QQQ position, kept open overnight deliberately, never the bot's own doing. The JS port was checked against the same real August 24 data used to validate the Python version and produced an identical $7.29 total, 18 round trips, before being trusted.

**The table shows symbol-summary rows, not individual trades** — # Trades, wins/losses split, Best Win, Worst Loss, Total P&L, Avg P&L/Trade, with a TOTAL row aggregating across symbols, matching the same visual pattern the Positions table already uses for its own TOTAL row. Colors reuse the existing `signClass()`/`signColor()`/`signPrefix()` helpers rather than introducing new logic; Best Win is always green, Worst Loss always red; a symbol with zero trades of either type shows "-", not `$0.00`, since a dash and a real break-even trade are different things. Detail columns (# Trades, Best Win, Worst Loss, Avg/Trade) are hidden on narrow screens via w3.css's own built-in `w3-hide-small` utility class, already loaded as part of the app's existing stack — no new responsive CSS needed. Fetches once when the Positions view loads, plus a manual Refresh button for re-pulling without leaving the view.

**A real, structural bug was caught and fixed before this ever worked — via the user's own live screenshot, not by review.** The new panel's content was almost certainly rendering correctly the whole time; the actual problem was that it was permanently invisible. The page's `render()` function hides every `.view-panel` element, then shows only the one exact match for the current view (`currentView + "Panel"`) — since the new section was a *second* `.view-panel` for the same "positions" view, it got hidden by that generic loop and never shown again, regardless of what its `innerHTML` actually contained. Fixed by removing it from that class entirely and controlling its visibility explicitly, alongside the main toggle, rather than through the generic one-panel-per-view mechanism that was never built to expect two panels for the same view. A second, smaller mistake in the same build: a CSS class (`btn-secondary`) was referenced for the Refresh button without ever confirming it existed anywhere in the app — it didn't. Caught by explicitly searching for every real button class before trusting the assumption; fixed by reusing the existing `.btn-cancel` styling instead, the closest real match for a low-stakes secondary action.

**Pagination is a known, deliberate gap, not an oversight — single page only for now (`page_size=100`).** Alpaca's activities endpoint works differently from the bars/series endpoint the user's own older reference code was written against: there's no `next_page_token` field on the response at all — the response is a plain array, and the *last item's own `id`* becomes the `page_token` for the next request. This was researched and confirmed directly from Alpaca's own documentation before writing anything, but the actual fetch-loop implementation itself is still on the list, not yet built. A day with more than 100 raw fill rows would currently only show its first page's worth of activity.

Revised to liquidate and lock out, with the lockout deliberately sticky through the session (verified numerically against the exact scenario that motivates it: a sell settling below the triggering value, thanks to spread, must not read as "back under the cap, resume").

**Visual fixes repeatedly demonstrated the same lesson from both directions.** The bolt toggle's icon color went through several real iterations — WCAG contrast math favored a dark icon, but real screenshots showed it disappearing into the fill; white was tried next based on that same visual evidence, and held up even once the math for the *other* fill color was checked too. Separately, an "armed" state built with `opacity:.45` was diagnosed as a genuine CSS problem for two full rounds before the real explanation surfaced: it was working exactly as designed, correctly dimmed because the screenshot was taken outside the configured trading window — not a rendering bug at all. Both threads ended the same way: trust what's actually on screen, and verify the actual state before assuming the code is wrong.

**Today, live: the design was confirmed against real trades, not just against tests.** The bot bought (capped at $100) and later sold a position on its own, matching the crossover logic exactly as designed weeks of conversation earlier. A separate, related scenario also got exercised for real: a bot-bought position that the user then manually added to (bringing it from $100 to $1000) was still correctly monitored by the bot's sell logic — confirmed directly from the code that the bot reads one shared, blended position from the broker, with no concept of "whose share is whose," and that a sell would close the entire position, manual addition included, not just its own original portion. End-of-day sell (15:55) was not exercised today — too early in the session for that specific trigger to have come up — and remains unverified live, though numerically confirmed at build time.

Two safety gaps were found and closed *after* the core feature already existed, each surfaced by the user thinking through a scenario the original design hadn't considered: importing settings onto a second device would have silently carried over an armed master switch and enabled symbols from the exporting device, since export/import predates automated trading and was never built with it in mind — fixed by forcing those specific fields off on import while preserving the numeric configuration. And the blue five-minute cue and the bot's own execution both used to span a broader 4am–8pm `isLive` window rather than actual regular trading hours — narrowed with a new, additional, shared gate rather than touching `isLive` itself, since that broader definition is still genuinely needed elsewhere (chart refresh, historical-date detection).

### V061 — August 16, 2026

Today's session added almost no new *capabilities* — it was a full day of small, precise fixes, and that turned out to be the right way to spend the day before "go time": rounding, timezone handling, list-position preservation, color consistency. None of these show up in a demo; all of them determine whether the tool holds up under real, fast, repeated use.

The clearest throughline across today specifically: **the same "one shared function, applied everywhere" pattern kept paying off, repeatedly, at increasing scale.** `round2()` (already existing) turned out to only be wired into a handful of places — a full audit found **16 separate sites** doing their own raw `>= 0` sign checks, each one a candidate for the exact bug that started the investigation: a value like `-0.001` displaying as `"0.00"` while still coloring red, because the color decision used the *raw* value instead of the *rounded, displayed* one. The loss-alert threshold (`CONFIG.lossAlertPct`) is a small but telling example of the same discipline in a different form — one config value drives three separate visual treatments (the POSITIONS stat card's hue, and both the per-row and TOTAL cells on the Positions table), rather than three independently-tuned thresholds that could quietly drift apart.
